# ADR 0011：运营失败队列与告警边界

- 状态：Accepted
- 日期：2026-07-24

## 背景

支付、邮件、存储和未来转码都可能在外部 Provider 或后续业务步骤中失败。Phase 4 之前，这些错误分别保存在 Order、PaymentEvent、MediaAsset 或服务端日志中，管理员需要登录服务器才能判断主要故障，也没有一致的处置记录。

## 决策

1. 新增 `OperationFailure` 作为面向运营的聚合故障记录，不替代 Order、PaymentEvent、MediaAsset 等领域事实；
2. 使用类别、错误码、Provider、来源类型和来源 ID 生成稳定指纹，同类重复故障累计次数；
3. 记录只保存脱敏后的摘要与错误信息，不保存支付回调原文、邮箱地址、Token、Cookie、AccessKey 或其他密钥；
4. 已处理故障保留处理人、时间和说明；相同故障再次发生时自动重新打开；
5. `ErrorReporter` 是 Provider Port，v0.1 实现结构化 Console 与带 HMAC-SHA256 签名的通用 Webhook；
6. 告警发送失败不得覆盖原业务错误，也不得让支付幂等事实回滚；告警自身失败降级写入结构化 Console；
7. 管理员导出是受保护、限量的可读快照，不视为备份。

## 备选方案

### 只依赖平台日志

实现简单，但不能满足“管理员无需查看服务器日志即可发现主要故障”，也缺少重复聚合和处置记录。

### 直接绑定 Sentry、飞书或 Slack

接入速度快，但会让核心操作流程绑定具体外部协议。公共核心先提供通用签名 Webhook，平台特定格式可由中继函数或后续 Provider 适配。

### 把所有错误写入一个任意 JSON 文档

扩展灵活，但容易混入个人数据和密钥，也违反严格 Schema 约束。因此采用有限字段和固定类别。

## 影响

- 后台可以统一查看支付、转码、邮件和存储故障；
- Order/PaymentEvent 等领域记录仍是支付审计的事实来源；
- Webhook 接收方必须校验时间戳与签名，并自行完成平台消息格式转换；
- 失败队列会增加少量 MongoDB 写入和索引成本；
- Sentry 仍是计划中的 Provider，选择时明确降级为 Console 并给出配置提示。
