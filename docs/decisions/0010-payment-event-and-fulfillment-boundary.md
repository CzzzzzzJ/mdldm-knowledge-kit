# ADR 0010：支付事件与权益发放事务边界

- 状态：Accepted
- 日期：2026-07-24

## 背景

支付平台回调可能重复、乱序或在授权过程中中断。本地默认 MongoDB 是单节点，不能把 Replica Set 事务作为 Demo 启动的强制条件；但支付成功与权益发放之间仍必须可审计、可恢复且不能重复发放。

## 决策

- `Product` 是当前可售商品，`OrderItem` 保存下单时的服务端价格与权益快照；
- 客户端只提交 `productId` 和支付方式，`Order` 总额完全由服务端商品计算；
- `PaymentEvent` 作为持久化 Inbox，以 `provider + eventId` 唯一索引实现事件幂等；
- XorPay 回调先验签，再校验订单 Provider、金额和币种；原始载荷只保存 SHA-256 摘要和必要审计字段；
- 支付确认后订单先进入 `paid`，权益发放使用 `fulfillmentStatus` 单独追踪；
- 每个 `OrderItem` 以自身 ID 作为 Entitlement 来源，并由唯一索引防止重复授权；
- 授权失败保留 `paid + failed` 状态，由管理员重试，不回退支付事实；
- Manual 和 Mock 也生成同构的 PaymentEvent，复用同一授权用例；
- v0.1 不要求 MongoDB Replica Set。上述持久化事件、原子状态认领和唯一约束构成可在单节点运行的恢复边界。

## 备选方案

### 回调中直接修改用户会员字段

实现简单，但无法表达单课、重复回调、失败重试和来源审计。

### 强制 MongoDB 多文档事务

事务边界更强，但会让默认单节点 Demo 无法运行，也不能覆盖支付平台与数据库之间的外部事务。

### 订单直接等同权益

不能覆盖邀请码、管理员授予、撤销、退款和分段会员有效期。

## 影响

- 订单的支付状态和授权状态必须分别展示；
- `paid + failed` 是需要运营处理的正式失败队列；
- 回调只有在事件与权益处理成功后返回成功，失败时让 Provider 重试；
- 退款回收在后续退款用例中撤销来源订单对应的 Entitlement；
- 若部署者已使用 Replica Set，可在未来 ADR 中把单次授权内部升级为 MongoDB 事务，但不能移除事件幂等与唯一约束。
